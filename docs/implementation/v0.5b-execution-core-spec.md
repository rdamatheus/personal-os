# Personal OS v0.5B — Execution Core CRUD Specification

Date: 2026-09-06
Status: implementation-ready specification
Depends on: v0.5A Canonical Data Layer

## 1. Objective

Move the primary execution flow of Personal OS from prototype/browser state to canonical Supabase persistence.

v0.5B covers the operational chain:

```text
Goal
  ↓
Project
  ↓
Task
```

with optional contextual relationships:

```text
Area → Goal / Project / Task
Goal → Route → RouteStep → Task
```

After v0.5B, Tasks, Projects and Goals must be usable from a fresh authenticated browser without relying on previous `localStorage` state.

The database becomes the source of truth for these modules.

---

## 2. Product principles for this release

### 2.1 Capture is not commitment
Ideas remain a separate domain. A Task represents something the user has intentionally promoted into execution.

### 2.2 Archive instead of destructive deletion
For Goals, Projects and Tasks, the normal “Delete” user action means archive/deactivate.

```text
active record
→ archive
→ hidden from default views
→ preserved in database/history
→ can be restored
```

No normal hard-delete UI is introduced in v0.5B.

### 2.3 Relationships must remain workspace-safe
All relationships must stay inside the same `workspace_id`. Existing composite foreign-key protections and RLS remain authoritative.

### 2.4 State changes are auditable
Create, edit, status change, completion, archive and restore should emit meaningful `activity_log` entries.

### 2.5 UI must reflect canonical state
The UI must not optimistically pretend that a change succeeded if the Supabase mutation fails. Errors must be visible and retryable.

---

## 3. Scope

### In scope

- Tasks: full user-facing lifecycle.
- Projects: full user-facing lifecycle.
- Goals: complete the lifecycle that is currently only partially implemented.
- Area association where useful in these forms.
- Goal → Project relationship.
- Project → Task relationship.
- RouteStep → Task relationship support at the data layer.
- Archive/restore flows.
- Direct repository-backed reads and writes.
- Removal of Tasks and Projects from the legacy polling bridge after validation.
- Migration/import safety for any legitimate local data.
- Activity log coverage.
- Cross-device persistence validation.
- RLS regression validation.

### Explicitly out of scope

- AI generation or AI recommendations.
- Full Route/RouteStep editor; that is v0.5C.
- Ideas and Decisions migration; that is v0.5D.
- Routines, Check-ins, Events and Journal; that is v0.5E.
- Final Today/History read model; that is v0.5F.
- Destructive hard-delete workflows.

## 4. Canonical entity lifecycle

## 4.1 Goal

Purpose: represent a desired outcome with a success condition and optional horizon.

### User-facing fields

- Title — required.
- Description — optional.
- Area — optional.
- Priority — low / medium / high.
- Target date — optional.
- Success criteria — optional but encouraged.
- Status.

### Canonical status vocabulary

```text
draft
active
paused
achieved
archived
```

The current database stores status as text, so v0.5B can adopt this vocabulary without a destructive schema migration.

### Actions

- Create Goal.
- Read/list Goal.
- Edit Goal.
- Pause / reactivate Goal.
- Mark Goal achieved.
- Archive Goal.
- Restore Goal.

### Archive rule

Primary archive mechanism: `archived_at`.

If an archived Goal previously had another semantic status, restoration should return it to a safe default of `active` unless a previous-status mechanism is introduced later. v0.5B does not require adding that schema complexity.

---

## 4.2 Project

Purpose: bounded initiative that advances a Goal or meaningful area of life.

### User-facing fields

- Title — required.
- Description — optional.
- Area — optional.
- Goal — optional.
- Priority — low / medium / high.
- Progress — 0–100.
- Start date — optional.
- Target date — optional.
- Status.

### Canonical status vocabulary

```text
planned
active
blocked
paused
done
archived
```

`idea` remains part of the broader domain contract, but v0.5B should not encourage Projects to be the capture inbox. Ideas should remain Ideas until promoted intentionally.

### Actions

- Create Project.
- Read/list Project.
- Edit Project.
- Change status.
- Update progress.
- Link/unlink Goal.
- Link/unlink Area.
- Archive Project.
- Restore Project.

### Progress rule

In v0.5B, Project progress remains user-editable because task-derived project progress is not yet fully specified.

Later releases may offer computed progress, but v0.5B must not silently change a user's Project percentage based on incomplete assumptions.

---

## 4.3 Task

Purpose: concrete executable action.

### User-facing fields

- Title — required.
- Description — optional.
- Area — optional.
- Project — optional.
- Route Step — optional.
- Priority — low / medium / high.
- Status.
- Due date/time — optional.
- Estimated minutes — optional.
- Energy required — optional.

### Canonical status vocabulary

```text
inbox
next
doing
blocked
done
cancelled
```

This follows the domain contract and gives the future Next Best Action engine enough semantic information.

The current database column is free text, so these values can be stored directly. The old `todo` value remains a legacy compatibility value and should be normalized when encountered:

```text
todo → next
```

### Energy mapping

The domain vocabulary is:

```text
low
medium
high
```

The existing database stores `energy_required` as integer. v0.5B should use a repository adapter rather than a destructive migration in this pass:

```text
low    → 1
medium → 2
high   → 3
```

Reads reverse this mapping.

A later schema-normalization migration can convert the column once all consumers use the canonical repository.

### Actions

- Create Task.
- Read/list Task.
- Edit Task.
- Change status.
- Mark done / reopen.
- Link/unlink Project.
- Link/unlink Area.
- Link/unlink Route Step when invoked from the route engine.
- Archive Task.
- Restore Task.

### Completion rule

Marking a Task `done` is a status update, not an archive.

```text
done = completed work still visible in history
archived = removed from active working set
```

## 5. Relationship rules

## 5.1 Goal → Project

A Project may optionally reference one Goal.

A Goal may have multiple Projects.

The relationship is not mandatory because some Projects may be maintenance/operational work rather than goal-bound work.

## 5.2 Project → Task

A Task may optionally reference one Project.

A Project may have multiple Tasks.

A Task without a Project remains valid.

## 5.3 Area relationships

Area remains optional for Goal, Project and Task.

UI should not force classification when the user wants fast capture/execution.

## 5.4 RouteStep → Task

The existing schema already allows a Task to reference a Route Step.

v0.5B preserves this capability but does not build the full Route Step conversion UI. v0.5C will expose “turn this Route Step into a Task” as a first-class flow.

## 5.5 Same-workspace guarantee

UI filters must show only candidate relationships from the active workspace, while database constraints/RLS remain the final security boundary.

## 6. UI plan

The current single-page dashboard can remain visually coherent, but its operational modules must stop mutating browser-only state.

### 6.1 Tasks surface

Minimum capabilities:

- list active Tasks;
- add Task;
- edit Task;
- status selector;
- priority selector;
- optional Project association;
- optional Area association;
- due date/time;
- estimated time;
- energy requirement;
- archive action;
- access archived Tasks / restore;
- loading, saving and error states.

Recommended default list ordering:

1. `doing`;
2. `next`;
3. `blocked`;
4. `inbox`;
5. due date ascending when present;
6. priority high → medium → low.

Completed Tasks should be available without crowding the active list.

### 6.2 Projects surface

Minimum capabilities:

- list active Projects;
- create Project;
- edit all supported fields;
- set status;
- update progress;
- associate Goal and Area;
- show number of related active Tasks;
- archive;
- view archived / restore.

Project detail does not need to become a new complex nested application in v0.5B. A modal, drawer or focused editor is sufficient if it keeps the cockpit simple.

### 6.3 Goals surface

The existing Routes page currently contains Goal creation. v0.5B should complete Goal management without fragmenting the concept.

Minimum capabilities:

- list Goals;
- create Goal;
- edit Goal;
- status change;
- mark achieved;
- archive;
- restore;
- show linked Projects count;
- preserve existing Goal ↔ Route relationship.

The product navigation may continue to expose the existing “Metas e rotas” route while the main dashboard's “Metas e ideias” wording is revised later when Ideas become persistent in v0.5D.

## 7. Repository/service rules

All new UI mutations must use the canonical repository layer introduced in v0.5A.

Forbidden for new v0.5B code:

- direct `localStorage` writes for canonical entities;
- new polling synchronization logic;
- bypassing the repository to duplicate mutation semantics in random components;
- service-role or secret keys in the browser;
- hardcoded user IDs or workspace IDs.

Required mutation context:

```text
workspaceId
userId
entity payload
```

Every mutation must remain scoped to the authenticated workspace.

## 8. Legacy bridge migration plan

The current `core-cloud-store.ts` bridge is transitional.

### Step 1 — read/import safety

Before removing Tasks/Projects from the bridge, detect whether the authenticated browser contains legitimate non-demo local records that are absent from the user's cloud workspace.

If so, import them once using stable mapping and then re-read from Supabase.

Do not upload demo seed IDs.

### Step 2 — switch UI reads

Tasks and Projects must load directly from repositories.

### Step 3 — switch UI writes

All Task/Project create/edit/status/archive actions use repositories.

### Step 4 — disable bridge participation

Remove Tasks and Projects from `hydrateCoreStore`, `syncCoreStore` and polling behavior.

Decisions remain temporarily on the legacy bridge until v0.5D.

### Step 5 — remove legacy browser dependency

When a fresh browser can reconstruct Tasks/Projects from Supabase and mutations remain correct, delete the obsolete Task/Project bridge compatibility code.

No local record should be silently discarded during this transition.

## 9. Activity log specification

Recommended events:

### Goals

- `goal_created`
- `goal_updated`
- `goal_status_changed`
- `goal_achieved`
- `goal_archived`
- `goal_restored`

### Projects

- `project_created`
- `project_updated`
- `project_status_changed`
- `project_progress_changed`
- `project_archived`
- `project_restored`

### Tasks

- `task_created`
- `task_updated`
- `task_status_changed`
- `task_completed`
- `task_reopened`
- `task_archived`
- `task_restored`

Metadata should be minimal and useful. Do not dump whole private record bodies into the audit log by default.

Example:

```json
{
  "from": "next",
  "to": "done",
  "project_id": "..."
}
```

## 10. Error and loading behavior

Every canonical screen must distinguish:

```text
loading
empty
ready
saving
error
```

Requirements:

- no infinite generic loader after a recoverable failure;
- mutation buttons disabled while the same mutation is pending;
- actionable error text;
- retry/reload capability;
- failed mutation must not be shown as persisted state;
- successful archive/restore must refresh the canonical list.

---

## 11. RLS and security validation

v0.5B does not weaken RLS.

Required validation:

1. User A creates Goal, Project and Task.
2. User A can read/update/archive/restore those records.
3. User B cannot read them.
4. User B cannot update them by guessing UUIDs.
5. User B cannot relate one of their records to User A's Goal/Project/Area.
6. A `viewer`, if used later, cannot mutate workspace records.
7. Frontend bundle contains only publishable Supabase configuration, never privileged secrets.

---

## 12. Cross-device validation

Definition:

```text
Device A creates/edits
→ Supabase persists
→ Device B signs into same account
→ Device B sees canonical state
```

Required scenarios:

- create Task on device/browser A, read on B;
- complete Task on B, see completed status after refresh on A;
- create Project on A, associate Task on B;
- edit Goal on B, see updated Goal/Route relationship on A;
- archive and restore from separate sessions.

`localStorage` must not be required for these scenarios.

---

## 13. Compatibility and schema strategy

v0.5B intentionally avoids unnecessary destructive migrations.

Current compatibility adapters remain acceptable for:

- Task `energy_required` integer ↔ low/medium/high;
- legacy Task `todo` → canonical `next`;
- current text priority columns.

If implementation reveals a constraint that cannot safely support the canonical lifecycle, introduce a small versioned migration with:

1. backward-compatible data conversion;
2. validation query;
3. documented rollback/mitigation;
4. security advisor rerun.

Do not alter migration history that has already been applied.

## 16. Rollback / failure strategy

v0.5B should be implemented incrementally so the last known working UI remains recoverable through Git history.

If a module migration fails:

1. do not delete canonical cloud records;
2. revert the frontend module to its last working commit if necessary;
3. keep repository layer intact unless it is the source of the defect;
4. do not restore the polling bridge as a permanent solution;
5. fix forward with a documented compatibility patch whenever practical.

No hard-delete migration is required for v0.5B.

---

## 17. Decisions already resolved

No user clarification is required before implementation for the following decisions:

- normal deletion means archive;
- database is canonical;
- `localStorage` is transitional/cache-only;
- RLS remains workspace-based;
- AI is not part of v0.5B;
- Goal/Project/Task relationships are optional, not forced;
- Project progress remains manually controlled in this release;
- Task status uses the richer domain vocabulary;
- energy uses an adapter against the current integer column;
- completed records remain historical records rather than being deleted.

## 18. Questions to raise only if implementation exposes a real blocker

The specification is intentionally sufficient to start implementation. Ask the user only if a concrete issue forces a product decision, for example:

- a destructive migration becomes unavoidable;
- existing real user data conflicts with the canonical mapping;
- a requested UI behavior would materially expand scope;
- a new paid/external service is required;
- a security trade-off cannot be resolved conservatively.

Otherwise proceed according to this specification and document implementation results.
