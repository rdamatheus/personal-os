# Personal OS v0.3 — Authentication & Core Persistence

Date: 2026-09-06

## Objective
Move the Personal OS prototype from anonymous browser-only state toward authenticated, workspace-scoped cloud persistence without replacing the approved Quiet Cockpit UI.

## Implemented
- Supabase browser client using the project publishable key.
- Global authentication gate for private routes.
- Email/password sign-in and sign-up screen.
- Google OAuth button and PKCE callback route prepared in code.
- Session persistence and automatic session refresh.
- Profile and active workspace lookup after authentication.
- Automatic personal workspace creation remains handled by the v0.2 database trigger.
- Sign-out control and cloud synchronization status indicator.
- Transitional persistence bridge for tasks, projects and decisions stored by the existing prototype in `localStorage`.
- Existing non-demo local core records are imported into Supabase when the user's cloud workspace is empty.
- Once hydrated, cloud data becomes the source used to seed the existing frontend store on page load.
- Build-time public Supabase URL and publishable key configured for GitHub Pages.

## Security decisions
- No service-role key or OpenAI key is present in the frontend or public repository.
- The Supabase publishable key is intentionally public and relies on RLS for authorization.
- RLS and workspace membership remain the security boundary for private records.
- Google login is authentication only; Gmail/Drive/Calendar scopes are not requested.

## Temporary compatibility layer
The current dashboard still writes its UI store to `localStorage`. To avoid a risky full UI rewrite in this release, `core-cloud-store.ts` acts as a temporary bridge:

1. authenticate user;
2. resolve personal workspace;
3. hydrate core records from Supabase before rendering the protected application;
4. preserve non-core local prototype state;
5. synchronize later changes to tasks, projects and decisions back to Supabase.

This bridge is intentionally transitional. The next refactor should replace browser polling with repository-backed hooks/services used directly by each module.

## Google OAuth remaining external configuration
The application code is ready, but Google sign-in also requires provider configuration outside the repository:

1. Set Supabase Auth Site URL to the production Personal OS URL.
2. Add the exact Personal OS callback URL to Supabase Auth Redirect URLs.
3. Create a Google OAuth Web Client.
4. Add the Supabase callback URL to Google Authorized Redirect URIs.
5. Enable the Google provider in Supabase and save Client ID / Client Secret there.

No Google client secret belongs in this repository.

## Validation target
- unauthenticated visitors are sent to `/login/`;
- authenticated users receive a profile + workspace context;
- each account sees only workspace-authorized data through RLS;
- browser core state can survive across sessions through Supabase;
- the existing dashboard remains visually intact.

## Next recommended release
v0.4 should remove the transitional localStorage bridge and make Goals, Routes, Route Steps, Projects, Tasks and Decisions use repository-backed CRUD directly. This is also the right point to make the existing route buttons open real persisted routes before connecting the OpenAI API.
